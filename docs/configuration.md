# Configuration

`install.sh` generates `deploy/.env`; [`deploy/.env.example`](../deploy/.env.example) documents
every variable. After editing it, run `./install.sh` again (`sudo ./install.sh` on Linux) to apply
the change; in production that run also moves TeamTAK to its latest release, unless
`--release current` is added. It re-creates the containers whose settings changed, and restarts TAK Server when its
`CoreConfig.xml` changed (`CERT_VALIDITY_DAYS`, `LDAP_UPDATE_INTERVAL`): the TAK clients are then
disconnected for about a minute. `docker compose restart` does not read `deploy/.env` again.

The settings worth knowing:

| Variable | Meaning |
|---|---|
| `CERT_VALIDITY_DAYS` | Validity of client certificates issued by enrollment. A certificate inside a zip stops working when it expires and nothing renews it; the platform records each expiry. A change applies to the certificates issued afterwards |
| `DEFAULT_MEMBER_CAP` | Member cap given to a new team (the administrator can change it per team) |
| `LOGIN_MAX_CODES_PER_EMAIL`, `LOGIN_MAX_CODES_PER_IP`, `LOGIN_MAX_FAILURES_PER_IP` | Hourly limits of the login codes |
| `LOGIN_RESEND_COOLDOWN_SECONDS` | Wait before another login code can be sent to the same address; the sign-in page shows the countdown (60; 5 in local mode, 0 turns it off) |
| `LOGIN_CHALLENGE_DIFFICULTY` | Work of the invisible anti-bot check asked before a login code is sent: the browser tries half this many SHA-256 on average (1000000 by default, from 10000 to 10000000). Raise it if scripts still get through; lower it if old phones take too long |
| `RECONCILE_INTERVAL_SECONDS` | Period of the reconciliation loop |
| `MONITOR_INTERVAL_SECONDS` | How often the platform looks at the machine, the services and TAK Server, and evaluates the alerts (60; 10 in local mode) |
| `AGENT_TOKEN` | Secret shared by the platform and the host agent, generated by the install |
| `RELEASE_REPOSITORY` | GitHub repository whose latest release the monitoring compares with the installed version: `owner/name`, or `off` to never ask GitHub. Empty: `Titou74/TeamTAK`, where TeamTAK is released |
| `P12_FORMAT` | `modern` (AES-256, what TAK Server's own scripts produce) or `legacy` (for Android 12 and older) |
| `TAK_API_MAX_HEAP`, `TAK_MESSAGING_MAX_HEAP`, … | Java heap sizes of TAK Server in MB; empty lets it size them from the machine's RAM |
| `TAK_CONNECTION_NAME` | Name of the server shown in ATAK and iTAK (`TeamTAK` by default) |
| `TAK_CLIENT_PORTS` | Ports of the machine TAK clients connect to, separated by commas (`8089` by default). See [Client ports](#client-ports) |
| `TAK_ADMIN_PORT` | Port of the machine where the platform's administrators open TAK Server's own administration pages (`8444` by default; `off`: not published; never `8443`, which TAK clients need). See [TAK Server's administration](#tak-servers-administration) |
| `SMTP_*`, `MAIL_FROM` | Outgoing e-mail; check it with `docker compose exec app teamtak send-test-mail you@example.org` |

The settings `install.sh` asks for, or reads from its options, are used on the first run only;
afterwards they live in this file.

## Client ports

TAK clients connect to TAK Server on port 8089 by default. Two situations call for other ports:

- **A network blocks 8089.** Some company, hotel or mobile networks only let a few ports out.
  List more ports, and the device on such a network uses one of them.
- **Another program of the machine already uses 8089.** Give another port instead of 8089.

```
TAK_CLIENT_PORTS=8089,4443
```

The first port of the list is the default one: it goes into the zips and QR codes. The others are
the alternative ports. When there are some, the dialog of an access in the web UI shows them:

- the QR code and zip tabs offer a choice of port, and the iTAK QR code and the zips follow it.
  A zip for an alternative port carries it in its file name (`alpha-shared-4443.zip`) and in the
  name of the connection on the device (`TeamTAK (4443)`), so a device holding several
  connections tells them apart; so does the iTAK QR code;
- the username and password tab lists them beside the default port, for a manual setup.

The ATAK QR code carries no port, so ATAK connects on its default port, 8089 (not checked on a
device): for another port, hand over a zip, or change the port in ATAK's server settings after
scanning.

Every port listed leads to the same TLS input of TAK Server (8089 inside its container), so TAK
Server's configuration does not change. Docker publishes them through
`deploy/data/docker-compose.ports.yml`, which `install.sh` writes from this list (it is part of
`COMPOSE_FILE`). After a change, run `./install.sh` again: TAK Server restarts with its new ports
and connected devices reconnect by themselves. Open the new ports in the firewall too.

The monitoring watches every port of the list, and shows a port listed here that Docker does not
publish (`./install.sh` not run again) as not published, with an alert
([monitoring](monitoring.md#the-monitoring-page)).

What is refused:

- 8443: TAK Server's API, which TAK clients reach with their certificate to read their channels
  and send files. ATAK and iTAK look for it on 8443 of the server whatever port they stream on, so
  the install always publishes it, as it is ([Channels on the devices](architecture.md#channels-on-the-devices)).
  An installation of 1.0.7 or older that listed 8443 here stops at the update, and says what to
  change.
- 8446 (enrollment) and the web interface's ports: 80 and 443 in production, 8480 and 8025 in
  local mode. In production, 443, the port almost every network lets through, belongs to the web
  interface.
- The port of TAK Server's administration (`TAK_ADMIN_PORT`, 8444 by default).
- A port another program of the machine listens on: the install says which, before building
  anything. Ports this stack already publishes are not counted.

Enrollment stays on 8446 only: a device on a network that also blocks 8446 needs the zip with
certificate, which connects without enrolling. A network that blocks 8443 lets the device stream
and see its team, but its channel list stays empty.

## TAK Server's administration

TAK Server has administration pages of its own: the metrics dashboard, inputs and data feeds,
missions, data packages, WebTAK. TeamTAK opens them to its administrators, and to nobody else,
without any certificate in the browser:

- Open the **TAK Server** link of the web UI's navigation (shown to administrators only), or
  `https://tak.example.org:8444` directly (`http://localhost:8444` in local mode).
- Without a session, or with the session of an account that is not an administrator, the browser
  is sent to the web UI, where the sign-in page is: nothing of TAK Server is shown. The session is
  the web UI's own, so signing in there is enough.
- Caddy serves that port. For each request it asks the platform whether the session belongs to an
  administrator, then passes the request on to TAK Server's 8443 over the Docker network,
  presenting a certificate of its own (`teamtak-admin-ui`, signed by the platform's authority and
  declared administrator in TAK Server by the install). TAK Server's own 8443, published for TAK
  clients, asks for a client certificate and gives the administrator role to none of theirs; no
  administrator certificate leaves the server.
- The [audit log](monitoring.md#audit-log) records who opened these pages, at most once an hour
  per administrator.

What to know:

- In TAK Server, every administrator acts under the one name `teamtak-admin-ui`: its logs cannot
  tell them apart. The audit log of the platform says who opened the pages, and when.
- The platform is the source of truth for TAK accounts, groups and client certificates. What is
  changed by hand in TAK Server's user and group pages is put back by the reconciliation, and a
  certificate revoked there is unknown to the platform. Use these pages to look, and to set up TAK
  Server itself.
- WebTAK needs HTTPS: it works in production, not in local mode, where this port is plain HTTP
  like the web UI.
- The certificate is valid two years, like the platform's own; the monitoring warns before it
  expires. To renew it, delete `deploy/data/tak/certs/teamtak-admin-ui*` and run `./install.sh`
  again.
- Another port: `TAK_ADMIN_PORT=9443`; none: `TAK_ADMIN_PORT=off`. Then run `./install.sh` again,
  and open or close the port in the firewall. Not 8443, which TAK clients need.
- An installation made before this setting existed, or with these pages on 8443 (1.0.7 and older),
  gets `8444` at the update, or `off` when 8444 is one of its TAK client ports or taken by another
  program; the install says so. Open 8444 in the firewall.

## Settings fixed at install

Some values are written into the data on the first run: changing them in `deploy/.env` afterwards
is not enough, and for the secrets and the names it breaks the installation:

- the secrets (`APP_SECRET`, `POSTGRES_PASSWORD`, `LDAP_ROOT_PW`, `LDAP_TAKSERVER_PW`,
  `LDAP_MANAGER_PW`, `TAK_DB_PASSWORD`, `TAK_CERT_PASSWORD`): the databases, the directory and the
  keystores were created with them, and without `APP_SECRET` the stored TAK passwords and zip
  certificates cannot be read;
- `LDAP_BASE_DN` and the certificate names (`ROOT_CA_NAME`, `INT_CA_NAME`, `SERVER_CERT_NAME`,
  `TAK_API_CERT_NAME`, `TAK_ADMIN_UI_CERT_NAME`);
- `PUBLIC_HOST`: TAK Server's certificate names the host given at install, and `install.sh` does
  not issue a new one;
- `TAK_VERSION`, `TAK_IMAGE` and `TAK_DB_IMAGE`: `./install.sh --upgrade-tak` changes them (README,
  "Upgrading TAK Server").

`TEAMTAK_VERSION` is not a setting: `install.sh` writes it at every run from git (the release tag
the checkout is on, or the last one followed by the number of commits since and the commit), and
the platform and agent images are tagged with it (`teamtak/app:1.0.1`). The images of other
versions are removed once the stack runs on the new one.

## Set from the web UI

The name of the server, who may sign up and whether new teams wait for approval, the thresholds
of the alerts, the backup schedule and passphrase, and the webhook are not in this file: they are
set from the web UI, in **Monitoring, Settings** (see
[sign-ups and team approval](architecture.md#sign-ups-and-team-approval),
[monitoring](monitoring.md) and [backups](backups.md)).

The name of the server tells it from the others an organisation runs (one per event, or per
domain name): it is shown on the sign-in page, in the browser tab and in small under TeamTAK at the
top left of every page. It also starts the subject of every e-mail the server sends:
`[Exercise North] Your sign-in code: …`, and for the alerts and the test e-mail
`[TeamTAK · Exercise North] Alert: …`. Up to 60 characters; empty, nothing is shown.
